1. Overview and test computer

The same MapReduce-style application is implemented three times: with processes and POSIX shared memory (mapreduce_shm), with processes and pipes (mapreduce_pipe), and with POSIX threads (mapreduce_thread). All three programs share the same tokenizer, hash table, partitioning and output code, so they differ only in how work is distributed and how partial results reach the master. They produce identical output. make test runs 145 checks: the sample files, chunk sizes of 1–7 bytes that cut almost every word, random files compared with an independent Python reference, and error cases. All 145 pass, and the programs are clean under AddressSanitizer, UBSan and ThreadSanitizer.

2. Program architecture

2.1 Common pipeline

  1. Input and partitioning. Each file is checked with stat(). A file larger than the chunk threshold (-c, default 8 MiB) is split into k = ⌈size / threshold⌉ nearly equal byte ranges. Every file, including an empty one, becomes at least one task (file index, start, end).
  2. Map. A mapper reads its range with pread() through a 64 KiB buffer. It converts ASCII letters to lowercase and treats every other byte as a separator, so world123test gives world and test. Words are counted in a local open-addressing hash table (FNV-1a hash, linear probing, words stored in an arena). Boundary rule: a word belongs to the chunk that contains its first letter. If the byte before start is a letter, the mapper skips the leading letters, because they belong to the previous chunk. If a word is still open at end, the mapper reads past end until the word finishes. This counts every word exactly once.
  3. Reduce. Partial tables of the same file are merged by adding the counts of equal words. Tables of different files are never mixed.
  4. Output. For each file, in command-line order, a single pass with insertion keeps the top 5 words, sorted by descending count with ties sorted alphabetically. If there are no words, the program prints No words found.

Each program limits the number of concurrently active mappers to N. Tasks beyond N are scheduled over time through a worker pool.

2.2 Implementation I: shared memory

The master creates a control region with shm_open, ftruncate and mmap(MAP_SHARED). It holds one entry per task: file, byte range, status and result size. The master fork()s one worker per task, keeping at most N alive at any time. A worker counts its range, creates its own result segment (/mr_res_<pid>_<task>) sized exactly for its serialized table, writes the table into it, records the size and status = 1 in the control region, and calls _exit(). Synchronization: the master reads an entry only after waitpid() reports that worker's exit, so the write has happened before the read and no lock is needed. Each control entry and each segment has exactly one writer. The master then opens and maps the segment, merges it, and releases it with munmap, close and shm_unlink. Merging happens while the other workers are still running. If an error occurs, the remaining workers are killed and reaped and every segment is unlinked. The test suite checks that no /dev/shm/mr_* objects remain.

2.3 Implementation II: message passing

The master fork()s a pool of W = min(N, tasks) long-lived workers, each with two pipes. The task pipe carries a fixed-size message (task id, file index, start, end, path length) followed by the file path. The result pipe carries a header (task id, status, byte count) followed by the serialized table. Each worker closes the ends it does not use, including the master-side ends of the pipes of previously created workers, so EOF is delivered correctly. The master sends one task to each worker and then poll()s the result pipes. When a result arrives, the master reads it completely, merges it, and sends that worker the next task. When no tasks are left, the master closes the worker's task pipe, the worker sees EOF and exits, and the master reaps it with waitpid(). Synchronization comes from the blocking pipe semantics alone. SIGPIPE is ignored, so a dead worker shows up as an error instead of killing the master.

2.4 Implementation III: POSIX threads

The main thread creates T = min(N, tasks) threads with pthread_create(). The threads take task indices from a shared counter that is protected by a mutex. This counter and an error flag are the only shared mutable data. Each thread counts into its own private table per file, so chunks of the same file that the same thread processes are combined locally and the hot path needs no lock. After pthread_join() of all threads, the main thread alone performs the reduce step, merging at most T tables per file. It takes over the first table without copying. One thread-specific problem appeared during measurement. glibc gives each thread its own malloc arena and grows it in small mprotect/mmap steps, and each step takes the process-wide address-space lock in write mode. This stalls the page faults of the other threads. The program therefore sets mallopt(M_TOP_PAD, 64 MiB) (see §5).

3. Experimental setup

The official files from AYBÜZEM were not available, so datasets with the required sizes were generated by bench/gen_data.py. The text is English-like: a Zipf-distributed vocabulary of 60,000 words with capitals, punctuation and digits.

  • D1: 1 MB
  • D2: 100 MB
  • D3: 4 × 25 MB
  • D4: 1, 5, 20 and 100 MB
  • D5: 1, 3, 8, 15, 30, 50, 75 and 100 MB

Each program measures itself with clock_gettime(CLOCK_MONOTONIC). Timing starts just before partitioning and parallel setup, and stops after the results have been printed and all workers and IPC objects have been cleaned up. Output goes to /dev/null. Every configuration (3 implementations × 5 datasets × N ∈ {1, 2, 4, 8, 16}) was run 5 times, and the median is reported. Files were warm in the page cache, and one warm-up run was done per dataset and implementation. The default chunk threshold was 8 MiB. The machine is a shared cloud VM, so repeated runs of the same configuration varied by roughly 10–25%. Differences smaller than that should not be over-interpreted.

6. Discussion

Which implementation performs best for small input files? Why?

Multithreading. On D1 it takes 11 ms, compared with 17 ms for shared memory and 17 ms for pipes. Table 4 isolates the fixed cost. Processing 10 tiny files takes 0.61 ms with one thread, 0.95 ms with one pipe worker, and 3.31 ms with shared memory, which forks a process and creates, maps and unlinks a segment for every task (about 0.3 ms per task when run serially). With little data, this setup cost is most of the runtime. A thread shares the address space, so it needs no page-table copy, no serialization and no system calls to exchange results. With the default 8 MiB threshold, D1 is a single task, so more workers cannot help: all curves in Figure 1 stay near 1 and the differences are noise. If D1 is split into 128 KiB chunks (Table 3), the process versions gain, for example shared memory falls from 25.8 to 9.4 ms. However, they only reach about the time the threaded version already needs with a single thread.

Which implementation performs best for large input files? Why?

With 4 workers, the threaded version has the lowest or nearly the lowest time on every large dataset:

  • D2: 245 ms (pipes 231, shared memory 305)
  • D3: 234 ms (pipes 237, shared memory 256)
  • D4: 217 ms (pipes 309, shared memory 320)
  • D5: 505 ms (pipes 638, shared memory 666)
Its single-worker time is also 20–30% lower: 663 ms on D2, compared with 850 ms and 916 ms. The process versions must serialize every partial table, copy it through the kernel (pipes) or through tmpfs pages (shared memory), and parse and hash it again in the master. Threads hand over tables in place, and the per-thread combining tables mean that only T tables per file are merged. Relative speedups at N = 4 are similar for all three versions (about 2.7–4.1×). The process versions start from a larger T(1), and their master's reduce work runs alongside the workers, which can push their speedup slightly above 4 on 4 cores. Such values are within the run-to-run noise. The best absolute D2 time is the pipe version at N = 8 (219 ms), effectively tied with threads at N = 16 (226 ms). Pipes and shared memory are close. Pipes reuse N long-lived workers, while the shared-memory version forks one process per task and creates one segment per task, so it pays more per chunk (Table 2).

How does increasing the number of workers affect execution time?

From 1 to 4 workers, the time falls almost linearly on all large datasets, because the work is CPU-bound (tokenizing and hashing) and the files are in the page cache. For example, D5 with threads goes from 1893 to 505 ms, and with shared memory from 2734 to 666 ms. Beyond 4 workers (the number of logical CPUs), the time stops improving and often gets worse. D5 with threads rises to 736 ms at N = 16, and D4 with pipes rises from 309 to 349 ms. The number of tasks also caps useful parallelism: D1 has 1 task, D2 has 13, D3 has 16, D4 has 18 and D5 has 39.

What are the overheads associated with process creation, thread creation, shared memory, and message passing?

  • Process creation: fork() copies page tables and file descriptors, and each later write triggers a copy-on-write page fault. The cost grows with the parent's memory, and the master's merged tables keep growing. waitpid() and process teardown add more. This is the main reason the shared-memory version is slowest with tiny chunks: with 64 KiB chunks it forks about 1600 processes and needs 2658 ms.
  • Thread creation: cheap, because only a stack and a kernel task are created and nothing is copied. Creating 10 threads costs well under a millisecond (Table 4). The hidden cost of threads is sharing: all threads use one address space, so mmap/mprotect and page faults contend on one lock. Figure 7 shows that with default malloc on D2, 16 threads take 414 ms instead of 214 ms, and system time was 0.45 s instead of 0.06 s.
  • Shared memory: no data is copied through the kernel. However, every segment costs shm_open, ftruncate, mmap, munmap and shm_unlink system calls plus page faults on first touch, and the data must still be serialized into a flat layout, because pointers are meaningless in another process.
  • Message passing: every byte is copied twice (user to kernel to user) in pieces no larger than the 64 KiB pipe buffer, which costs extra system calls and context switches. In return, pipes need no explicit synchronization, and long-lived workers spread the fork cost over many tasks.

Does splitting a large file into smaller chunks always improve performance?

No. Table 2 and Figure 6 show this. Without splitting (128M), the 100 MB file is one task, so only one core works and every version takes about 550–610 ms. Splitting into 16–32 MiB chunks gives the best results for the process versions (about 230–255 ms). Much smaller chunks hurt the process versions badly: at 64 KiB, pipes take 736 ms and shared memory 2658 ms, because each chunk adds a fork or a message, a fresh table that has to be serialized, and a merge. Threads stay at about 165–230 ms across the whole range, since an extra chunk costs them only a mutex operation and they keep using one table per file. The best chunk size is one that produces a few tasks per worker without the per-task overhead dominating.

How does an uneven distribution of file sizes affect workload balancing?

When each file is one task, the largest file decides the total time. In D4, the 100 MB file is 79% of the data. Without splitting (Table 5), 4 workers improve the time only from about 748 to 661 ms (shared memory), a speedup of about 1.1–1.3, because three workers finish early and sit idle. With 8 MiB chunks, D4 becomes 18 similar tasks served from a shared pool, and the speedup at N = 4 rises to 3.82 (shared memory), 3.64 (threads) and 3.02 (pipes). Dynamic scheduling, where the next free worker takes the next task, is what balances the load. Static assignment of files to workers would not.

Why might increasing the number of workers beyond the number of available CPU cores fail to improve performance?

The task is CPU-bound, and with 4 logical processors at most 4 mappers can run at the same time. Extra workers only time-share the same cores and add costs: context switches, more process or thread creation, more partial tables to merge, more cache and memory-bandwidth pressure, and for threads more contention on the address-space lock. The master, which also needs CPU time to merge results, has to compete with them. This is why times at N = 8 and 16 are equal to or worse than at N = 4 (Table 1).

What are the advantages and disadvantages of processes compared with threads for this application?

Processes:

  • Strong isolation: a crashing mapper cannot corrupt the master, and the failure is detected through its exit status.
  • No accidental sharing, so no data races.
  • No contention on one address space, so they scale smoothly to the core count.
  • Costs: expensive creation, explicit IPC with serialization and copying, and more resources to clean up (segments, descriptors, zombies).
Threads:
  • The cheapest creation and the fastest result exchange, because tables are merged in place.
  • Lower memory use, and the best absolute times in our measurements.
  • Costs: a bug in one thread can corrupt the whole program.
  • All shared state must be synchronized correctly. Here this is kept to one mutex-protected counter.
  • Hidden contention inside the shared address space (malloc arenas and page faults) can reduce scaling unless it is addressed.
For this read-mostly, CPU-bound workload, threads are the better engineering choice. The process-based designs pay for safety with IPC overhead.

7. Conclusion

All three designs produce identical results and keep at most N mappers active. Threads had the best absolute times on D1, D3, D4 and D5, and were effectively tied with pipes on D2. Message passing and shared memory scale well up to the number of cores, but they spend extra time on process creation and on moving serialized tables, and the shared-memory version additionally creates and destroys one segment per task. Chunking a file into a moderate number of word-safe chunks, together with dynamic scheduling, is essential for large and unequal inputs. Using more workers than cores does not help.
