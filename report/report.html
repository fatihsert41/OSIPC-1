1. Overview and test computer

The same MapReduce-style application is implemented three times: with processes and POSIX shared memory (mapreduce_shm), with processes and pipes (mapreduce_pipe), and with POSIX threads (mapreduce_thread). All three programs share the same tokenizer, hash table, partitioning and output code, so they differ only in how work is distributed and how partial results reach the master. They produce identical output. They match the provided expected results and, on all files of D1–D5, an independent Python reference. make test runs 145 checks: the sample files, chunk sizes of 1–7 bytes that cut almost every word, random files, and error cases. All 145 pass, and the programs are clean under AddressSanitizer, UBSan and ThreadSanitizer.

2. Program architecture

2.1 Common pipeline

  1. Input and partitioning. Each file is checked with stat(). A file larger than the chunk threshold (-c, default 8 MiB) is split into k = ⌈size / threshold⌉ nearly equal byte ranges. Every file, including an empty one, becomes at least one task (file index, start, end).
  2. Map. A mapper reads its range with pread() through a 64 KiB buffer. It converts ASCII letters to lowercase and treats every other byte as a separator, so world123test gives world and test. Words are counted in a local open-addressing hash table (FNV-1a hash, linear probing, words stored in an arena). Boundary rule: a word belongs to the chunk that contains its first letter. If the byte before start is a letter, the mapper skips the leading letters, because they belong to the previous chunk. If a word is still open at end, the mapper reads past end until the word finishes. This counts every word exactly once.
  3. Reduce. Partial tables of the same file are merged by adding the counts of equal words. Tables of different files are never mixed.
  4. Output. For each file, in command-line order, a single pass with insertion keeps the top 5 words, sorted by descending count with ties sorted alphabetically. If there are no words, the program prints No words found.

Each program limits the number of concurrently active mappers to N. Tasks beyond N are scheduled over time through a worker pool.

2.2 Implementation I: shared memory

The master creates a control region with shm_open, ftruncate and mmap(MAP_SHARED). It holds one entry per task: file, byte range, status and result size. The master fork()s one worker per task, keeping at most N alive at any time. A worker counts its range, creates its own result segment (/mr_res_<pid>_<task>) sized exactly for its serialized table, writes the table into it, records the size and status = 1 in the control region, and calls _exit(). Synchronization: the master reads an entry only after waitpid() reports that worker's exit, so the write has happened before the read and no lock is needed. Each control entry and each segment has exactly one writer. The master then opens and maps the segment, merges it, and releases it with munmap, close and shm_unlink. Merging happens while the other workers are still running. If an error occurs, the remaining workers are killed and reaped and every segment is unlinked. The test suite checks that no /dev/shm/mr_* objects remain.

2.3 Implementation II: message passing

The master fork()s a pool of W = min(N, tasks) long-lived workers, each with two pipes. The task pipe carries a fixed-size message (task id, file index, start, end, path length) followed by the file path. The result pipe carries a header (task id, status, byte count) followed by the serialized table. Each worker closes the ends it does not use, including the master-side ends of the pipes of previously created workers, so EOF is delivered correctly. The master sends one task to each worker and then poll()s the result pipes. When a result arrives, the master reads it completely, merges it, and sends that worker the next task. When no tasks are left, the master closes the worker's task pipe, the worker sees EOF and exits, and the master reaps it with waitpid(). Synchronization comes from the blocking pipe semantics alone. SIGPIPE is ignored, so a dead worker shows up as an error instead of killing the master.

2.4 Implementation III: POSIX threads

The main thread creates T = min(N, tasks) threads with pthread_create(). The threads take task indices from a shared counter that is protected by a mutex. This counter and an error flag are the only shared mutable data. Each thread counts into its own private table per file, so chunks of the same file that the same thread processes are combined locally and the hot path needs no lock. After pthread_join() of all threads, the main thread alone performs the reduce step, merging at most T tables per file. It takes over the first table without copying. The program also calls mallopt(M_TOP_PAD, 64 MiB), so malloc grows each thread's heap in large steps; §6 explains why.

3. Experimental setup

The official D1–D5 datasets from AYBÜZEM were used:

  • D1: 1 MB
  • D2: 100 MB
  • D3: 4 × 25 MB
  • D4: 1, 5, 20 and 100 MB
  • D5: 1, 5, 10, 25, 50, 75, 100 and 2 MB

Here 1 MB = 106 bytes. The files repeat the same English paragraph, so each file has only 26 distinct words. Each program measures itself with clock_gettime(CLOCK_MONOTONIC). Timing starts just before partitioning and parallel setup, and stops after the results have been printed and all workers and IPC objects have been cleaned up. Output goes to /dev/null. Every configuration (3 implementations × 5 datasets × N ∈ {1, 2, 4, 8, 16}) was run 5 times, and the median is reported. Files were warm in the page cache, and one warm-up run was done per dataset and implementation. The default chunk threshold was 8 MiB, which gives 1, 12, 12, 17 and 35 tasks for D1–D5. Repeated runs of the same configuration varied by roughly 5–20%, so smaller differences should not be over-interpreted. All scripts are in bench/ (make bench).

6. Supplementary experiment: a large vocabulary

The official files have only 26 distinct words, so the frequency tables are tiny and almost no result data has to be moved between workers. To see how the designs behave when the partial results are large, the same experiments were also run on synthetic text with the same file sizes and a Zipf-distributed vocabulary of 60,000 words (bench/gen_data.py; results in bench/synthetic/).

With large tables, threads are clearly fastest with one worker, because the process versions must serialize every partial table and parse and hash it again in the master. Without the M_TOP_PAD setting, 16 threads needed 414 ms instead of 214 ms, and the system time rose from 0.06 s to 0.45 s (Figure 7). glibc gives every thread its own malloc arena and grows it in small mprotect steps, and each step takes the process-wide address-space lock in write mode. This stalls the page faults of all other threads. Processes have separate address spaces and do not suffer from this. With the official data the setting makes no difference (55 vs. 54 ms at N = 16), because the tables stay small.

7. Discussion

Which implementation performs best for small input files? Why?

Multithreading. On D1 it takes 1.9 ms, compared with 2.4 ms for shared memory and 2.3 ms for pipes. With so little data, setup cost is most of the runtime. Table 4 isolates that cost. Processing 10 tiny files takes 0.48 ms with one thread, 0.89 ms with one pipe worker, and 4.62 ms with shared memory, which forks a process and creates, maps and unlinks a segment for every task (about 0.4 ms per task when run serially). A thread needs no page-table copy, no serialization and no system calls to exchange results. D1 is a single task at the default threshold, so more workers cannot help and all curves in Figure 1 stay near 1. When D1 is split into 128 KiB chunks (Table 3), the best times fall to about 1.1–1.9 ms at N = 4, and the threaded version is still fastest. Beyond that point, the extra workers cost more than the parallel work saves.

Which implementation performs best for large input files? Why?

On the official data the three versions are close. At N = 4 the fastest version is:

  • D2: threads (53.7 ms)
  • D3: threads (46.4 ms)
  • D4: threads (72.7 ms)
  • D5: threads (126.6 ms)
Shared memory is usually last. Because each table holds only 26 words, the IPC payload is a few hundred bytes per task. Almost all of the time goes to the identical scanning loop, which processes about 524 MB/s per core. The differences that remain come from per-task costs. Threads pay only a mutex operation per task. Pipes pay one message round trip and reuse N workers. Shared memory pays a fork(), a new segment and a waitpid() per task, which also makes its single-worker time the slowest (225 ms on D2, vs. 183 ms for pipes and 191 ms for threads). When the partial results are large (§6), threads win by a wider margin, because the process versions must serialize, copy and re-hash every table.

How does increasing the number of workers affect execution time?

From 1 to 4 workers, the time falls almost linearly. The average speedup at N = 4 over D2–D5 is 3.43 for shared memory, 3.46 for pipes and 3.61 for threads, because the work is CPU-bound and the files are in the page cache. Beyond 4 workers (the number of logical CPUs), there is no consistent further gain. The best time at N = 8 or 16 is within about ±20% of the best at N = 4, which is close to the measurement noise. The number of tasks also caps useful parallelism, since D1 has a single task.

What are the overheads associated with process creation, thread creation, shared memory, and message passing?

  • Process creation: fork() copies page tables and descriptors, and each later write triggers a copy-on-write page fault. waitpid() and process teardown add more. With 64 KiB chunks (about 1,500 tasks), the fork-per-task shared-memory version needs 223 ms on D2, compared with 67 ms at 8 MiB.
  • Thread creation: cheap, because only a stack and a kernel task are created. Ten threads cost well under a millisecond (Table 4). The hidden cost of threads is sharing one address space: malloc and page-fault contention appear when the threads allocate a lot of memory (§6).
  • Shared memory: no data passes through the kernel. However, each segment costs shm_open, ftruncate, mmap, munmap and shm_unlink plus first-touch page faults, and tables must be serialized because pointers are meaningless in another process.
  • Message passing: every byte is copied twice (user to kernel to user) in pieces of at most 64 KiB, with extra system calls and context switches. Pipes need no explicit synchronization, and long-lived workers spread the fork cost over many tasks. With 64 KiB chunks, pipes need 70 ms, compared with 223 ms for shared memory.

Does splitting a large file into smaller chunks always improve performance?

No. Table 2 and Figure 6 show this. Without splitting (128M), the 100 MB file is one task, so only one core works and every version takes about 184–196 ms. Moderate chunks of 256 KiB to 16 MiB are two to four times faster. Very small chunks hurt the process versions: shared memory needs 223 ms at 64 KiB, because every chunk adds a fork or a message, a fresh table and a merge. Threads stay at about 49–60 ms across that range, since an extra chunk costs them only a mutex operation. Large chunks of 32 MiB leave only 3 tasks for 4 workers. The best chunk size gives a few tasks per worker while the per-task overhead stays small.

How does an uneven distribution of file sizes affect workload balancing?

When each file is one task, the largest file decides the total time. In D4, the 100 MB file is 79% of the data. With one task per file (Table 5), 4 workers give a speedup of only 1.11–1.28, because three workers finish early and sit idle. With 8 MiB chunks, D4 becomes 17 tasks of similar size served from a shared pool, and the speedup at N = 4 rises to 3.08–3.35. Splitting large files and scheduling dynamically, where the next free worker takes the next task, is what balances the load.

Why might increasing the number of workers beyond the number of available CPU cores fail to improve performance?

The task is CPU-bound, and with 4 logical processors at most 4 mappers can run at the same time. Extra workers only time-share the same cores and add costs: context switches, more process or thread creation, more partial tables to merge, cache pressure, and for threads more contention on the shared address space. The master, which needs CPU time to merge results, has to compete with them. Table 1 confirms this: times at N = 8 and 16 are no better than at N = 4.

What are the advantages and disadvantages of processes compared with threads for this application?

Processes:

  • Strong isolation: a crashing mapper cannot corrupt the master, and the failure is detected through its exit status.
  • No accidental sharing, so no data races.
  • No contention inside one address space.
  • Costs: expensive creation, explicit IPC with serialization and copying, and more resources to clean up (segments, descriptors, zombie processes).
Threads:
  • The cheapest creation and the fastest result exchange, because tables are merged in place.
  • Lower memory use, and the best or near-best times in every experiment.
  • Costs: a bug in one thread can bring down the whole program.
  • All shared state must be synchronized correctly. Here this is kept to one mutex-protected counter.
  • Shared-address-space contention (malloc arenas, page faults) can limit scaling unless it is addressed.
For this CPU-bound, read-only workload, threads are the most efficient choice. The process designs trade some speed for isolation.

8. Conclusion

All three designs produce identical, verified results and never run more than N mappers at a time. On the official datasets they scale almost linearly up to the 4 available cores and differ only slightly, because the work is dominated by scanning text and the partial results are tiny. Shared memory with fork-per-task has the highest per-task overhead, pipes are in between, and threads have the lowest. These differences grow with very small chunks or large vocabularies. Splitting large files into moderate, word-safe chunks combined with dynamic scheduling is essential for large and unequal inputs, and using more workers than cores does not help.
